# Reflection — 网段发现性能专项（2026-08-30）

## 做对了什么

- **先调查后动手**：两份行号级前后端调查把「26 万上限」「万条卡顿」还原成 8 个具体瓶颈，方案按收益/风险排序，避免了盲目重构。
- **计划-切片-审查节奏**：每个 Task 独立提交 + 规格/质量双审查，Task 5 的 Critical（短扫描 terminal 漏检）在审查中被抓住而不是靠用户报告。
- **契约先钉死再接线**：后端分页 envelope、显式空串语义、ids=[] no-op 等先有测试，前端再对齐——两端语义分叉只出现过一次（group/label 编码），当场被 handoff 记录阻止。

## 踩了什么坑

1. **迁移修复引入死循环**：把流式游标改成「物化批次」时，没考虑「整批都是无法解析行」的情况——UPDATE 0 行 → 同一批被重新选中 → 死循环，全量测试挂起 10 分钟 CPU 100%。教训：**批处理循环的每一层谓词都要论证单调推进**（最终用 `id > last_seen_id` 保证），且长跑测试要加 timeout 守卫。
2. **mtr `hubs` 键名**（本专项外、同周内）：解析外部工具 JSON 输出时键名必须对着真实输出或权威文档确认，"hop/hubs" 这类近义词最容易想当然。
3. **handoff 中「不要重做」清单的价值**：接手会话靠第 1 节的状态表直接进入 Task 5 审查，节省了整轮重放。

## 结构性观察

- 前端至今零自动化测试，tsc+build 是唯一门禁；useDiscovery 的竞态密度（abort/generation/nudge/visibility）值得首批 vitest 覆盖。
- 批量 API 的「分块 + 跨块原子」模式可以复用到 servers 侧既有接口。
- 性能类改动最大的验证资产是 EXPLAIN 证据与有界性 mock 配方——它们把「感觉快了」变成可重放断言。
